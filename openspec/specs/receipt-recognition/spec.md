# receipt-recognition Specification

## Purpose
拍一张小票就能少打几个字：在用户显式开启并配置 API Key 后，把图交给视觉模型，由模型直接给出金额、商家、时间、分类、支付渠道与标签。手动添加图片仍预填到面板让用户确认；截屏识别出金额则直接记账，不再要求二次确认——默认关闭、未开启时不上传。

## Requirements

### Requirement: 选图后 SHALL 尝试识别

用户添加图片、或系统检测到截屏后，系统 SHALL 尝试用视觉模型识别这张图。手动添加图片时 SHALL 按结果预填金额、分类、标签、账户、备注与日期，并由用户点完成保存；系统检测到截屏且识别出金额时 SHALL 直接创建一笔支出并保存原图，MUST NOT 再要求用户打开面板确认。识别不出金额时 MUST NOT 自动入账。

MUST NOT 使用设备本地 OCR。仅当用户显式开启视觉识别并保存了 API Key 时，系统 SHALL 调用其配置的视觉模型；未开启、未保存 Key 或平台不支持时，系统 MUST NOT 发起任何识别请求、也 MUST NOT 上传图片，仅在用户添加图片后提示去设置里配置。

#### Scenario: 认出一张小票

- **WHEN** 用户已开启视觉识别并保存了 API Key，添加一张写着「合计 ¥44.50」「金豆餐厅 消费小票」的截图
- **THEN** 系统把图片发送给配置的视觉模型，面板金额变成 44.50、分类预选「餐饮」、标签填入候选、备注填入商家名，且用户可以改

#### Scenario: 检测到截屏后自动记账

- **WHEN** 视觉识别已启用，系统检测到一张能读出金额的付款截屏
- **THEN** 识别完成后直接创建一笔支出（原图随交易保存），通知显示「已自动记账 ¥X」，不再要求用户点完成

#### Scenario: 截屏没读出金额

- **WHEN** 系统检测到截屏但没有识别出金额
- **THEN** 不自动入账；保留已识别出的分类/商家预填，通知提示点击手动补金额

#### Scenario: 没配置时不识别、不上传

- **WHEN** 用户没有开启视觉识别（或没有保存 API Key），添加一张小票图
- **THEN** 不发起任何网络请求，面板提示「视觉识别未开启，可在设置里配置」，其它功能正常

#### Scenario: 已经有输入时不覆盖

- **WHEN** 用户已经填了金额 30 又加了一张图
- **THEN** 金额保持 30，识别只填空白字段（分类/标签/备注）

#### Scenario: 认不出金额

- **WHEN** 图片里没有可识别的金额
- **THEN** 面板给出「没认出金额，手动填一下」的提示，其它输入不变

### Requirement: 截屏识别出金额 SHALL 自动入账

截屏路径识别出正整数金额时，系统 SHALL 直接创建一笔支出并保存原图/截图；MUST NOT 再写待确认队列等用户点完成。
字段兜底：分类按「识别分类 → 上次使用的支出分类 → 其他 → 第一个支出分类」，账户按「识别账户 → 上次使用的账户 → 不选账户」，
日期用识别出的支付时间、缺失时用当前时间，备注用商家名，标签只在「自动打标签」开启时写入；MUST NOT 自动创建账户。

同一时间、金额与备注命中去重键时 MUST NOT 重复创建交易或重复保存图片，通知 SHALL 说明「这笔已经记过了」。
自动落库失败时 SHALL 降级为手动确认（保留识别结果），不得静默丢图或丢识别结果。

#### Scenario: 金额识别成功

- **WHEN** 截屏识别结果包含 amount_cents=1800、分类餐饮、商家名
- **THEN** 直接写入 18.00 的支出，附带原图；通知显示已自动记账，不需要再点确认

#### Scenario: 重复识别同一张图

- **WHEN** 同一张截图被重复识别，时间/金额/备注一致
- **THEN** 不新增第二笔交易，也不新增第二张附件，通知显示已经记过

#### Scenario: 自动落库失败

- **WHEN** 数据库或附件写入失败
- **THEN** 保留识别结果进入待确认队列，通知提示自动记账失败、可手动确认

### Requirement: 视觉识别 SHALL 显式开启且密钥安全保存

视觉识别 SHALL 默认关闭；只有用户在设置中显式开启并保存 API Key 后才 SHALL 生效。

API Key SHALL 保存在系统安全存储（Android Keystore / iOS Keychain），MUST NOT 写入
`app_state`、SQLite、日志、错误提示或遥测；清除 API Key SHALL 同时关闭识别。

#### Scenario: 默认关闭

- **WHEN** 用户首次安装并打开金豆
- **THEN** 视觉识别开关为关闭，添加图片不识别，也不发起网络请求

#### Scenario: 开启但没有 Key 不生效

- **WHEN** 用户打开开关但还没有保存 API Key
- **THEN** 设置页显示「已开启但还没有 API Key：识别不会生效」，添加图片时不上传

#### Scenario: 密钥不落库

- **WHEN** 用户保存 API Key 后检查本地数据库与日志
- **THEN** 看不到明文 Key，只能看到「已保存」这类状态

#### Scenario: 清除 Key 自动关闭

- **WHEN** 用户在设置里清除 API Key
- **THEN** 识别开关同时关闭，之后添加图片不再上传

### Requirement: 视觉识别 SHALL 走 OpenAI 兼容协议且失败不影响记账

视觉识别 SHALL 使用 OpenAI 兼容的 `POST {baseUrl}/chat/completions`：图片 SHALL 以
`image_url` 的 base64 data URL 发送，请求 SHALL 带 `Authorization: Bearer <API Key>`；
服务地址与模型名 SHALL 可配置，默认 `https://api.deepseek.com` 与 `deepseek-flash`，
地址尾部斜杠 SHALL 被归一化。请求 SHALL 关闭推理输出、把温度设为 0、限制输出长度，
并要求 JSON 输出（见「结构化字段 SHALL 由模型直接给出」）。

云端请求超时、鉴权失败、限流、服务错误或返回内容不可解析时，系统 SHALL 给出可读提示并保持
金额与分类原样，MUST NOT 阻塞保存；由于不再有本地 OCR，MUST NOT 假装回退到本地识别。
请求与响应日志 MUST NOT 包含 API Key 或图片内容。

#### Scenario: 只改配置就能换厂商

- **WHEN** 用户把 `baseUrl` 改为另一家 OpenAI 兼容服务并改模型名
- **THEN** 识别仍能工作，不需要改代码

#### Scenario: 鉴权失败

- **WHEN** 云端返回 401
- **THEN** 面板提示「视觉识别失败，可以手动填」，金额与分类仍可手动填写并保存

#### Scenario: 超时

- **WHEN** 云端请求超时
- **THEN** 面板提示失败原因，不再等待，用户可继续手动记账

#### Scenario: 畸形响应

- **WHEN** 云端返回 200 但内容不是 JSON
- **THEN** 抛出可读错误（不含 Key 与图片），面板提示手动填，仍可保存

#### Scenario: 没有可用字段

- **WHEN** 云端返回 `{}` 或全是 null
- **THEN** 只提示「没认出金额，手动填一下」，仍可保存

### Requirement: 结构化字段 SHALL 由模型直接给出

请求 SHALL 用 `response_format: {"type": "json_object"}` 要求模型只返回一个 JSON 对象，字段为
`amount_cents`（整数，单位分）、`merchant`、`paid_at`（`yyyy-MM-dd HH:mm:ss`）、`category`、
`account_hint`、`tags`。系统 MUST NOT 再从识别文本里规则解析金额、日期或分类。

本地 SHALL 只校验取值、不猜测：金额必须是正整数且不超过 1,000,000 元，否则按「没认出」处理；
分类 SHALL 只接受词表内的规范名（先做别名归一化）；账户 SHALL 只接受词表内的规范名；
标签 SHALL 只保留词表内的名字、去重后最多 2 个；时间解析失败或年份越界 SHALL 丢弃该字段。
模型返回未知字段或把 JSON 包在 ```json 代码块里 SHALL 仍能解析。

#### Scenario: 微信账单截图

- **WHEN** 用户识别一张显示「臻汁煌（金山软件园店）」「-18.00」「支付时间 2026年10月18日 18:20:49」「支付方式 零钱」的账单截图
- **THEN** 金额为 18.00、备注为商家名、时间为 2026-10-18 18:20:49、分类为餐饮、账户为微信
- **AND** MUST NOT 把时间里的「49」或状态栏的「20:51」当成金额

#### Scenario: 模型自创分类

- **WHEN** 模型返回 `"category": "饮品"`（不在词表内）
- **THEN** 该字段被丢弃，面板不预选分类，也不因此新建分类

#### Scenario: 金额越界或不是正数

- **WHEN** 模型返回 0、负数或超过 1,000,000 元的金额
- **THEN** 按「没认出金额」处理，面板提示手动填

#### Scenario: 响应里带杂物

- **WHEN** 模型除了已知字段还多返回了 `"type": "json_object"`，或把 JSON 包在代码块里
- **THEN** 已知字段仍被正确取出

### Requirement: 设置页 SHALL 提供识别自检

设置页「截图记账」SHALL 提供「测试识别」入口：用当前表单里的服务地址、模型与 API Key（未保存的也算）
向一张内置的合成小票发一次真实请求，并 SHALL 明确显示「识别正常」或失败原因。
测试 MUST NOT 保存设置、MUST NOT 发送用户自己的图片，也 MUST NOT 修改开关。

#### Scenario: 配置正确

- **WHEN** 用户填好 Key 点「测试识别」
- **THEN** 显示「识别正常：测试小票 ¥12.34」

#### Scenario: Key 无效

- **WHEN** 云端返回 401
- **THEN** 显示「测试失败：API Key 无效或没有权限」

#### Scenario: 模型不支持图片

- **WHEN** 云端返回 200 但认不出测试小票的任何字段
- **THEN** 显示「接口通了，但没读出测试小票（模型可能不支持图片输入）」

#### Scenario: 金额认错

- **WHEN** 云端返回的金额不是 12.34 元
- **THEN** 显示读成了多少、应为多少，并提示换一个支持图片的模型

#### Scenario: 没填 Key

- **WHEN** 页面里既没有刚输入的 Key，也没有已保存的 Key
- **THEN** 提示「先填一个 API Key 再测试」，不发请求

### Requirement: 识别 SHALL 可插拔且可关闭

识别 SHALL 通过 `ReceiptRecognizer` 接口注入；Web 或不支持的平台 SHALL 使用空实现（不提示、不报错），
测试 SHALL 能注入假识别器。识别失败 MUST NOT 阻塞记账。

#### Scenario: Web 上不识别

- **WHEN** 用户在 Web 版添加图片
- **THEN** 不出现识别相关的提示，也没有报错，其它功能正常

#### Scenario: 识别抛错

- **WHEN** 识别器抛异常
- **THEN** 面板显示「识别失败」一句话，金额与分类保持原样，仍可正常保存

### Requirement: 识别 SHALL 匹配分类、标签与账户

识别结果落到面板时，分类 SHALL 先做名称归一化（去空格/标点/全半角）与别名匹配，命中同收支类型的已有分类则直接预选；未命中时 SHALL 仅展示「将新建」候选，等用户保存时再按分类创建规则落库。

标签 SHALL 由模型从固定词表里给出（单笔最多 2 个），本地只做词表校验与去重，同名/近似名复用，创建时机与分类相同；账户 SHALL 只把模型给出的规范名映射到已有账户，匹配不到时沿用上次使用的账户，MUST NOT 自动创建账户。

#### Scenario: 别名命中已有分类

- **WHEN** 模型返回分类「吃饭」，本地已有分类「餐饮」
- **THEN** 面板预选「餐饮」，不新建分类

#### Scenario: 分类不存在

- **WHEN** 识别出「咖啡」，本地没有同名或别名分类，且用户开启了自动新建
- **THEN** 面板显示「将新建分类：咖啡」；用户点保存后才创建，取消则什么也不留下

#### Scenario: 自动打标签

- **WHEN** 模型返回标签 `["微信支付", "咖啡"]`，本地已有标签「微信支付」
- **THEN** 面板复用「微信支付」，再补充「咖啡」一个候选，总数不超过 2 个

#### Scenario: 账户只匹配不新建

- **WHEN** 模型给出的支付渠道在本地没有对应账户
- **THEN** 面板沿用上次账户，不新建账户，也不改变用户已选账户
