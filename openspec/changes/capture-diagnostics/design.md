# Design

## Context

动机见 `proposal.md` —— Why；行为契约见 `specs/capture-diagnostics/spec.md`。

当前链路的形态决定了观测点该打在哪：

- 捕获事件先由 Kotlin（`AccessibilityCaptureService` / `NotificationCaptureService`）产生，经进程内总线 `CaptureRuntime`（Kotlin）转发给 `CaptureService` 里的 headless 引擎，再由 Dart 的 `CaptureRuntime`（同名不同语言）做规则匹配与入账。
- 大模型有两次调用：`VisionReceiptRecognizer`（截图识别）与 `CloudCaptureRuleGenerator`（规则生成），两者都在解析后丢弃原始 `content`。
- 既有日志出口只有一条：Dart 调 `log` 方法 → Kotlin `Log.i("BeanCapture")`。真机上不可见，重启即丢。
- 存储层没有任何迁移设施，业务状态都放 `app_state`（key-value）；原生存 `SharedPreferences`。

## Goals / Non-Goals

**Goals:**

- 让「为什么这次没记账」「模型到底说了什么」在手机上可自查、可导出。
- 记录覆盖到 Dart 尚不存在的时刻（引擎未就绪、服务未起、窗口读不到）。
- 记录对业务结果零影响：不改变任何判定，不新增网络请求，不新增数据库迁移。
- 记录量有界，长期开着也不会撑大存储。

**Non-Goals:**

- 不修任何已知断点（指纹稳定性、证据腐烂、通知规则互相覆盖）——本变更只做观测，修复另行提案。
- 不做远程上报、埋点统计、崩溃收集。
- 不记录用户输入的账单正文、不落整屏截图。
- 不提供按字段检索/过滤/图表等高级分析能力。

## Decisions

### D1 扁平事件模型，而非文本日志

一条记录 = `{seq, at, kind, package?, target?, outcome, reason?, detail}`，`detail` 是该 kind 专属的自由字段。kind 为有限枚举：`gate_closed` / `tree_captured` / `notif_captured` / `no_rule` / `pending_rule` / `no_extraction` / `entry_written` / `write_failed` / `llm_recognize` / `llm_rule_gen` / `learn_skipped` / `event_dropped` / `window_missing`。

**理由**：需求要回答的是三个具体问题（模型说了什么、为什么停在哪一步、服务是否在跑），结构化字段才能让诊断页与导出直接对齐；纯文本需要人再解析一遍。

**备选**：直接保留 logcat 文本行 —— 无法跨源合并、无法在页面上折叠展开，否决。

### D2 双源记录：Dart 写 `app_state`，原生写 `SharedPreferences`

原生侧事件（`gate_closed` / `event_dropped` / `window_missing`）恰好发生在 Dart 不可用时，必须由 Kotlin 自己落盘；Dart 侧事件（规则、模型、入账）走已有的 `app_state`。

**理由**：单源都不成立——Dart 单源记不到「引擎没起来」，原生单源处理不了 JSON 与模型原文。

**备选**：全部经 `log` 通道交给 Kotlin 统一写入 —— 通道本身在引擎未就绪时也不可用，仍会丢最关键的记录，否决。

诊断页读取时按 `at` 升序合并两源；`seq` 只在各自源内单调，跨源只用时间排序。

### D3 两源同时追加一份 JSONL 到 App 私有目录

`<app files>/diag/events.log`，每行一条事件 JSON；单文件上限 512 KB，超出滚成 `events.log.1`（只保留一份旧文件）。

**理由**：排查时用户常常连着 adb，`adb pull` 一下就能拿到全量，不必解锁手机翻页面；也避免「App 被系统杀掉后页面数据丢失」时无据可查。

**备选**：只做页面展示 —— 排查时要把手机递给我看，不可行，否决。

### D4 记录分两层：摘要常留，证据限量

事件摘要保留最近 200 条；含完整页面文本或模型原文的「证据」单独一个环形，只保留最近 10 条，事件里用 `evidenceId` 引用。

**理由**：一次树 dump 约 20–60 KB，若每条事件都带，200 条就是 MB 级；而排查一次问题只需要最近那几笔的完整现场。

**备选**：全部只存摘要 —— 没有树文本就无法判断「是没匹配上还是匹配了但抽错」，等于白记，否决。

### D5 导出默认脱敏，但保留金额与指纹

导出时抹掉商户名、订单号与 6 位以上连续数字；保留「带货币符号或两位小数」的金额形态与页面指纹（8 位十六进制）。

**理由**：金额是判断「错多少」的唯一依据，指纹是判断「规则为何不命中」的唯一依据；商户名与订单号对排查几乎无用，是纯隐私负担。

**备选**：导出前把所有数字都抹成 `#`（与 `desensitizeTree` 一致）—— 会把金额一起抹掉，导出即失效，否决。

### D6 埋点只加在既有决策点旁，不引入新分支

每个事件都写在已有的 `if`/`return` 旁边，记录调用一律 fire-and-forget 并吞掉异常；记录层不得成为业务的前置依赖。

**理由**：spec 要求「记录失败不影响业务」；把埋点做成 `try/catch` 包住的旁路，是唯一能不改变现有控制流的做法。

### D7 采集常开，不设「诊断模式」开关

只要自动记账开关是开的，诊断记录就一直记，环形容量兜底。

**理由**：要排查的恰恰是「下一次支付为什么没记」，如果默认关着，用户要等下一次出问题才想起去开——那一笔已经错过了。

**备选**：仅在设置里手动开启诊断模式 —— 使用时序出错概率高，否决。

### D8 服务状态来自独立的运行标志，而非授权查询

诊断页状态卡的「后台服务在跑」由原生侧维护的最后启动/停止时间戳推断，不复用 `isAccessibilityEnabled()`。

**理由**：授权「已开启」与服务「正在运行」是两件事；本次要排查的就是「授权开着但一次也没记」，必须能区分这两者。

### D9 同类事件 1 秒内合并计数

同一 `kind` + 同一 `package` 在 1 秒内重复发生时合并为一条并累加 `count`。

**理由**：`TYPE_WINDOW_CONTENT_CHANGED` 很密集，即便原生侧已有 300ms 去抖，仍可能刷屏把 200 条环形冲掉，反而看不见关键事件。

## Risks / Trade-offs

- [记录开销拖慢捕获路径] → 埋点全为旁路、无 await 依赖、异常吞掉；单条 JSON 相对一次树 dump 可忽略。
- [树快照可能含聊天内容等敏感文本] → 只在「抓到树」时留证，完整记录仅 10 条，落在 App 私有目录，导出脱敏；不落整屏截图。
- [双源合并后时间顺序有毫秒级错乱] → 两源都用设备本地时钟（`System.currentTimeMillis` / `DateTime.now()`），同一设备无偏移；排序只用于展示，不参与业务。
- [事件洪泛冲掉关键记录] → 1 秒合并计数 + 完整证据独立环形，关键事件（入账、模型返回）不受刷屏影响。
- [环形淘汰掉用户想追溯的那一次] → 诊断页顶部显示「上次入账/上次捕获」，并支持一键导出；过期即不可追回，这是有界存储的必然代价。
- [导出文件被外部应用读取] → 导出走系统分享（用户主动选择目标）或保存到 App 私有目录，不写公共相册/下载目录。

## Migration Plan

无数据库迁移：`app_state` 是 key-value，新增 `diag_event:` / `diag_evidence:` 前缀即可；原生 `SharedPreferences` 新增独立文件 `capture_diag`。旧版本读到这些 key 会当作未知数据，不解析也不删除。

发布方式与现有链路一致（tag → GitHub Releases）。回滚只需移除诊断入口与埋点；已写入的记录与 `diag/` 文件无害，可在设置里清空。

## Open Questions

- 诊断页是否需要按 kind 过滤或关键字搜索。当前事件量（200 条）下时间倒序滚动即可用，等真机上翻不动再加，不影响本次的任务拆分。
