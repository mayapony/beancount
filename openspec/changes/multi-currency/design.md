# Design

## 一句话：本位币是唯一的"钱"，原币只是档案

```
交易金额字段（amountCents） = 本位币分            ← 所有统计/余额/净值/导出都用它
originalAmountCents        = 原币分（可空）      ← 只在非 CNY 时有值
currency                   = 原币代码（默认 CNY）
ratePpm                    = 1 外币 = 多少 CNY × 10^6（可空）
```

为什么不让统计改成"先折后加"：那会把汇率逻辑渗进每一个聚合点（洞察、余额、净值、日分组、搜索小计、导出），
任何一处漏掉就是数字错误。把折算集中在**写入那一刻**，读路径完全不变——这是这次改动的核心取舍。

代价：汇率是"记账当时"的快照，事后汇率变了不会回溯（这是账本的正确行为：历史成本）。

## 换算

```dart
int baseCentsOf({required int originalCents, required int ratePpm}) =>
    (originalCents * ratePpm + 500000) ~/ 1000000;   // 四舍五入到分
```

用整数而不是 double：`10000 * 7.25` 在 double 里是 `72499.999…`，乘完再 round 会在边界上抖。

## 汇率存储与默认值

- `ratePpm` 存整数（`7.25 → 7250000`），显示时 `ppm / 1e6` 保留 4 位；
- `app_state` 里按币种记 `rate_usd` 之类（实际键：`fx_USD`），下次记该币种默认填上次值；
- 不联网取汇率——离线优先的产品，宁可用"上次的值 + 手动改"。

## 面板交互

选中账户币种 ≠ CNY 时，金额卡下方多一行：

```
汇率  USD 1 = ¥ 7.25  ›
```

点击弹一个小输入框；保存时把 `ratePpm` 与币种一起交给 `NewTransaction`。
输入框里填的是**外币金额**（用户手里拿的是外币小票），面板顶部金额保持原样，只是语义变了。

## 显示

- 明细行：金额位置显示 `US$100.00`，下面一行小字 `≈ ¥725.00`（`US$`/`€` 用一个小映射表，未知币种直接写代码）。
- 详情：金额下方加「汇率 1 USD = 7.25 CNY」与「折合 ¥725.00」。
- 账户行：名字后面加币种标签（CNY 不显示，避免噪音）。

## 迁移

`schemaVersion = 5`：
- `accounts.currency` 默认 `'CNY'`（`alterTable` + 默认值，老行自动填 CNY）；
- `transactions.currency` 默认 `'CNY'`，`original_amount_cents` / `rate_ppm` 可空。

老数据 `originalAmountCents == null`，显示逻辑据此走"CNY 分支"，不需要回填。

## 关键决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 折算位置 | 写入时算好本位币 | 读路径零改动，聚合不会漏 |
| 金额字段语义 | 保持本位币 | 所有既有代码与测试继续成立 |
| 汇率精度 | ppm 整数 | 避免 double 误差；4 位小数够用 |
| 导出 | 只写本位币 + CNY | 宁可丢原币档案，也不能让回灌金额翻倍 |
| 实时汇率 | 不做 | 离线优先；手动 + 记忆更可预期 |

## 风险

| 风险 | 应对 |
|---|---|
| 忘记传汇率导致金额为 0 | 非 CNY 且未提供汇率时抛 ArgumentError，用例覆盖 |
| 汇率填写错误 | 面板显示换算后的结果，保存前能看出来 |
| 导出丢原币 | 写进 spec 的已知限制；导出前页面提示一句 |
| 旧数据没有原币 | `originalAmountCents == null` 即 CNY 分支 |
