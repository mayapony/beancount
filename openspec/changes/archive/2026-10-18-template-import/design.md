# Design

## 管线：只加"入口"，不动落库

```
用户选文件
   ↓
[统一入口] parseImportFile(bytes, fileName)
   ├─ xlsx（PK 头） → excel 读第一个工作表 → matrix
   ├─ 文本 → UTF-8 解码，失败回退 GBK → CsvToListConverter → matrix
   ├─ 识别表头（找含「交易时间」或「类型+金额+时间」的行）
   ├─ 支付宝 / 微信 → 专用解析 → List<ParsedRow>
   └─ 否则 → BeeCount 解析（现有 parseBeeCountCsv）
   ↓
已有的 planImport（去重/分类创建/账户创建）→ apply → 报告
```

这样预览、去重（同一秒同金额同备注）、错误报告、附件都**沿用现有实现**，新格式不引入第二套导入逻辑。

## 识别与表头定位

- 表头行：第一个满足「含 `交易时间`」或「含 `类型` 且含 `金额`」的行，允许前 30 行内出现。
- 平台判定：`收/支` 列存在时——前言含「支付宝」→ 支付宝，含「微信」→ 微信。
- 列定位按**列名**而不是位置：支付宝用 `交易分类/收/付款方式/交易状态/商品说明`，微信用 `交易类型/支付方式/当前状态/商品`，两者共用 `交易时间/交易对方/收|支/金额|金额(元)/备注`。

## 编码

1. `utf8.decode(bytes)` 严格模式；
2. 抛错则 `gbk.decode(bytes)`（`gbk_codec`，纯 Dart）；
3. 都失败 → 致命错误「无法识别文件编码」。

支付宝 Windows 导出用 GBK；微信 2023 年后是 UTF-8。先试 UTF-8 再回退，对两者都成立。

## 金额与时间

复用 `parseAmountToCents` 与 `parseBeeCountTime`：先把 `¥`、`元`、千分位逗号清掉再解析；时间格式两家都是 `YYYY-MM-DD HH:mm:ss`。

## 分类映射

| 对方分类（含即可） | 本地分类 |
|---|---|
| 餐饮 / 美食 | 餐饮 |
| 交通 / 出行 | 交通 |
| 服饰 / 日用 / 购物 | 购物 |
| 医疗 / 健康 | 医疗 |
| 教育 / 培训 | 教育 |
| 酒店 / 旅游 | 旅行 |
| 运动 / 户外 | 运动 |
| 数码 / 电器 | 数码 |
| 住房 / 物业 | 居家 |
| 宠物 | 宠物 |
| 红包 | 红包（收入） |
| 工资 | 工资（收入） |
| 理财 / 投资 | 理财（收入） |
| 其它 | 支出→其他，收入→其他收入 |

匹配不到时不报错，落到兜底分类——对方分类种类型号比本地多得多，报错只会让用户卡住。

## 账户

统一归到平台账户：「支付宝」/「微信支付」。原始支付方式（余额宝、招商银行储蓄卡(1234)）**不进备注**——它既不是商品名，也会让备注变噪音；需要时以后再加"支付方式"字段。

## 关键决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 是否新建一套导入管线 | 否，只加解析入口 | 去重/报告/附件已有且被测试覆盖 |
| 账户映射 | 归到平台 | 避免自动创建几十个"银行卡(1234)" |
| 未知分类 | 兜底不报错 | 对方分类太杂，报错会挡住整批 |
| GBK | 加 `gbk_codec` | 支付宝导出就是 GBK，不解码等于不支持 |
| Excel | 加 `excel` | xlsx 是 zip + XML，手写解析不划算 |
| 跳过行 | 报告里带行号 + 原因 | 用户要能核对"钱去哪了" |

## 风险

| 风险 | 应对 |
|---|---|
| 平台改列名 | 列名别名表 + 缺列时给出"缺哪列"的可读错误 |
| 表头前说明文字很长 | 前 30 行内找表头，找不到才算失败 |
| 红包/转账被算成收支 | 转账类行 `收/支` 为 `/`，按跳过规则处理 |
| Excel 单元格是数字类型 | 统一 `'$cell'.trim()`，金额走同一清洗 |
| 大文件内存 | 与现有 CSV 一致（万级行已验证） |
