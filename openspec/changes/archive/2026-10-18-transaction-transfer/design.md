# Design

## 数据模型：一条记录，两端账户

不采用「支出 + 收入两条腿」：那会让统计、对账、删除三处都要处理配对关系，任何一处忘了就是脏数据。

```
transactions
  type          = transfer
  category_id   = NULL
  account_id    = 转出账户
  to_account_id = 转入账户
  amount_cents  = 金额（> 0）
```

### 迁移 v1 → v2

- `category_id` 由 NOT NULL 改为可空；
- 新增 `to_account_id`（可空，引用 accounts）；
- 用 drift 的 `TableMigration(transactions)` 重建表并复制数据（SQLite 不能原地放宽 NOT NULL）。

迁移必须做到：**历史交易的 id/金额/分类/备注/去重键一个不变**，索引在迁移后仍然存在。测试用「构造 v1 库 → 打开新版本 → 校验数据与索引」的方式验证，而不是靠人工点。

### 去重键

`dedupeKeyFor(...)` 增加可选 `toAccountId`：**只有转账才传**，其余路径拼出的字节与现在完全一致——所以历史 48 笔的键不需要重算，重复导入依旧幂等。

## 余额与统计

| 位置 | 规则 |
|---|---|
| 账户余额 | 转出账户：`−amount`；转入账户：`+amount`。查询改成 `UNION`（或两次聚合）后合并 |
| 账户笔数 | 两端都 +1 |
| 明细当天小计 | 只累加 `expense` / `income`，转账不计 |
| 明细概览 / 日均 | 同上 |
| 洞察 | `InsightsRepository` 的查询加 `type != 'transfer'` |
| 净资产 | 转账不影响合计（一减一加） |

## 界面

### 记账面板

支出 / 收入 / **转账** 三段。切到转账时：

```
[支出] [收入] [转账]
从  [招商银行卡 ▾]   →   到  [支付宝 ▾]
[金额卡 + 备注行]
[键盘]
```

分类网格隐藏；「从」「到」复用现有的账户选择面板（同一个 `_AccountSheet`）。

### 明细行与详情

- 行标题：`账户A → 账户B`（没有备注时）；有备注时备注优先，副标题仍显示流向。
- 金额：用 `palette.transfer` 中性灰，`showSign: false`。
- 详情页：字段行显示「从」「到」两行，分类行隐藏；编辑走面板的转账模式。

### 搜索

- 类型胶囊多一个「转账」；
- 关键词匹配集合在转账时用两端账户名（没有分类名）。

## 关键决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 单记录 vs 两条腿 | 单记录 | 统计/对账/删除只有一处逻辑 |
| 分类列 | 改为可空 | 转账本就没有分类，塞哨兵分类会污染分类树与占比 |
| 账户删除 | 有转账引用同样拒绝 | 与「被引用不可删」一致 |
| 导入转账 | 仍跳过 | 映射 BeeCount 的 From/To 到两端需要新的导入规则，留给后续 change |
| 去重键 | 仅转账纳入转入账户 | 否则会改变历史键值，破坏导入幂等 |

## 风险

| 风险 | 应对 |
|---|---|
| 迁移重建表丢数据/索引 | 专门写迁移测试（v1 构造 → 打开 → 数据与索引都在），并覆盖"迁移后还能记账" |
| `categoryId` 可空引发的空指针 | 编译期强制改：`TransactionRow.category` 变可空后，所有使用点都必须处理转账分支 |
| 账户余额 SQL 变复杂后算错 | `AccountBalance` 用例覆盖「只有转账」「转账 + 收支混合」两种情形 |
| 明细小计把转账算进去 | 日分组小计只看 `isExpense`/`isIncome`，用例断言转账日的小计为 0 |
