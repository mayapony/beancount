# Design

## Context

- 现有接缝：`ReceiptRecognizer`（图→文字）+ `parseReceiptText`（文字→`ReceiptGuess`）负责视觉识别；`EntryWriter` + `TransactionRepository` 负责写入；`dedupeKeyFor` 只做「同一份数据导入两次」的幂等。
- `receipt-recognition` spec 的「MUST NOT 直接创建交易」只约束手动选图路径；本 change 的自动入账是新行为，两者不冲突。
- 平台：仅 Android 侧载、不上架；`AndroidManifest.xml` 已有 `INTERNET` / `REQUEST_INSTALL_PACKAGES`。
- 截图自动检测由 pending change `screenshot-pending-read`（截屏 pending 态可靠读取）负责，本设计只把它当作截图兜底的触发来源，不在此展开检测细节。

## Goals / Non-Goals

**Goals:**

- 三类采集（无障碍 / 通知 / 截图）收敛为同一候选管线，金额解析、去重、写入只写一份。
- 提取规则是数据文件，可热更、可回滚、可在设备上自愈生长。
- 事后审计（通知 + 最近自动记账列表）替代事前确认。
- 采集与规则存储本地，规则生成走用户配置的云端模型。

**Non-Goals:**

- 不做中心化规则库 / 众包共享（n=1 不成立，且与隐私冲突）。
- 不做 iOS / Web。
- 不改动手动选图的 `receipt-recognition` 行为。
- 不做浮窗记账按钮（用通知代替，少一个高危权限）。

## Decisions

### D1: 采集来源统一为 adapter 接缝

决策：定义 `CaptureSource` 抽象，产出统一的 `CaptureCandidate`（金额、方向、商家/备注、时间、来源、rawText、surface 指纹）。三个实现：无障碍、通知、截图。

理由：三条路都只做「拿文本 + 元数据」，后续解析、去重、写入走同一条管线，避免长出三份确认逻辑。

备选：各来源各自写入 quick_entry_sheet → 拒绝，会演变成三份不一致的路径。

### D2: 原生瘦 shim + 业务逻辑留在 Dart

决策：无障碍 / 通知服务用 Kotlin 薄封装（服务生命周期 + 读控件树/通知 + 经 EventChannel 转发到 Dart），业务逻辑（规则匹配、候选合并、自愈学习、`EntryWriter`、通知）全在 Dart。

理由：无障碍服务绑定期间系统保活 App 进程，Flutter 引擎可常驻，实时入账可行；业务逻辑与既有 `EntryWriter` / `TransactionRepository` 同侧，复用不复制。无障碍 / 通知是 Android 系统组件，无法纯 Dart。

备选：Kotlin 直接写 SQLite → 拒绝，会复制 drift 的写入与去重逻辑，schema 归属也会打架。

### D3: 规则是数据 + 受限 DSL

决策：提取规则存为 App 私有目录下的版本化 JSON（数字版本 + last-known-good 指针）。DSL 只表达：`surface 指纹匹配`、`金额抽取（文本正则 / 邻近标签）`、`方向`、`排除词`。

理由：可热更、可 diff、可回滚；无远程代码执行面。

备选：AI 生成 Dart 代码作规则 → 拒绝，等于自装 RCE，且无法机械验证 / 回滚。

### D4: 用页面结构指纹而非 activity 作规则 key

决策：以「节点数分桶 + 关键标签集合 + bounds 布局」的哈希作 surface 指纹，规则模糊匹配到指纹。

理由：微信 / 支付宝几乎全 App 复用同一 activity，用 activity 作 key 会让一条规则覆盖全 App，必然误匹配。

### D5: 自愈闭环 —— 留证是控件树，真值来自当次入账

决策：采集层维护白名单包的结构化树快照环形缓冲（约 60s，仅结构）。未命中时，把截图当次入账的金额作为真值，连同「包名 + 指纹 + 树快照」留证；规则由用户配置的云端模型生成——上传脱敏后的树快照（结构 + 金额形态，不含整屏截图），产出受限 DSL 规则。

理由：规则作用在树，证据必须是树；真值来自用户那次截图入账的金额，不用 OCR 反推。规则生成与视觉模型共用同一 OpenAI 兼容端点（沿用 `receipt-recognition` 配置），视觉模型继续只做截图金额识别与「树不可读」兜底。

### D6: 规则入库要回放验证 + 信任阶梯

决策：新规则必须通过「正例解出真值 + 负例（同包其它页面）静默」才生效；生效后进入灰度（前 3 次命中仍需确认），3 次无修改才升自动；任一次被用户改金额 → 降级 + 存为回归样本。

理由：一条「能匹配但匹配错」的规则比不匹配更糟——它会关掉「没记上」的告警。信任阶梯把可验证性变成运行时机制。

### D7: 树不可读的页面走永久截图路径

决策：当白名单包某 surface 的树为空（自绘 / Canvas / WebView 未开语义 / FLAG_SECURE），标记该包 + surface 为「截图优先」，不反复尝试生成规则。

理由：这类失败永远修不好规则，反复生成只是浪费；拓扑决策与选择器是两类问题。

### D8: 候选合并去重与 dedupeKeyFor 分离

决策：候选层先按「来源包名 + 金额 + ±120s」合并成待入账候选，再进 `EntryWriter`；`dedupeKeyFor` 仍用于导入幂等，语义不动。

理由：多源实时捕获的重复窗口与「同一文件导入两次」的幂等语义不同，复用会产生误合并或漏合并。

### D9: 事后审计 = 通知 + 最近自动记账列表

决策：每笔自动入账弹「已记账」通知（深链到列表），并提供「最近自动记账」列表（今天 N 笔，可改可删）。不做事前确认。

理由：通知是易失的，列表才是「让用户改」的持久记录；列表同时补上「漏记」那一半的可见性（spec 的「失效 SHALL 可感知」）。

## Risks / Trade-offs

- [静默记错：错规则匹配错金额] → D6 回放验证 + 信任阶梯 + 任一次修改即降级；列表可见可改。
- [静默漏记：服务被杀 / 目标应用改版导致零捕获] → 「最近自动记账」列表的「今天 N 笔」+ 连续零命中心跳（spec 失效 requirement）。
- [OEM 杀后台导致非实时] → 无障碍服务绑定期保活进程；若仍被杀，退化为「打开时补记」，D2 的 shim 保留持久候选队列兜底。
- [Android 13+ 侧载受限设置：无障碍 / 通知使用权默认灰] → 设置页给引导文案（进「应用信息 → 允许受限设置」），不靠技术解决。
- [隐私：读全屏的观感 + 规则生成上传树快照] → 白名单包 + 仅这些包前台才读 + rawText 不落库 + 默认关闭；规则生成上传脱敏树快照且仅用户配置后。
- [规则 DSL 过度复杂] → DSL 只暴露少量策略原语（文本正则 / 邻近标签），由 LLM 选择并参数化，不手写金额/方向启发式。

## Migration Plan

- 能力默认关闭，无既有数据迁移。
- 规则文件带版本与 last-known-good；出问题时回滚 = 关闭开关 + 恢复到上一版规则文件，不动账本数据。
- 首次启用仅作用于白名单包，逐个验证后再扩。

## Open Questions

- 白名单包最终集合（先微信、支付宝，云闪付与银行 App 视需要再加）—— 可在实现时定，不改 spec 与任务划分。
- 无障碍服务是否需要前台服务进一步保活 —— 待实机 OEM 测试后定，不影响任务拆分。
