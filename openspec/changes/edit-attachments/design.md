# Design

## 用既有的两个原语，不加新概念

| 需求 | 手段 |
|---|---|
| 加图 | `AttachmentRepository.add(transactionId, bytes, fileName)` — 与记一笔同一条路径 |
| 删图 | `attachmentsOf(id)` 拿到 `Attachment` 行 → `remove(attachment.id)` — 已带引用计数回收 |

详情页只负责"选图 → 调仓储 → 刷新 `_images`"，不碰文件系统。

## 页面结构

```
图片 · 2
[缩略图 ✕] [缩略图 ✕] [+ 添加图片]
```

- ✕ 是缩略图右上角的小圆钮（16×16 深色半透明），点它弹确认（「删除这张图片？」）。
- 「+ 添加图片」是 96×96 的虚线方块，点了先弹来源选择（相册/相机），再走注入的 `ImagePickFn`。
- 增删成功后调 `_loadExtras()` 重新读图（与编辑保存后同一条刷新路径）。

## 依赖注入

`TransactionDetailPage` 新增可选参数 `pickImage`（`ImagePickFn`，与记一笔同一个类型）。
为空时不显示「添加图片」——截图脚本与部分测试因此不需要平台通道。
明细页/搜索页打开详情时把同一个 `systemImagePicker()` 传进去（`kIsWeb` 时为 null）。

## 删除的边界

- 确认弹窗必须出现：误删图片没有撤销。
- `remove()` 内部已经有"仅当没有其它记录引用同名文件时才删文件"的逻辑，直接复用。
- 删除后如果这是最后一张，图片区整段消失（`if (_images.isEmpty) return;` 已如此）。

## 关键决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 是否新建编辑页 | 否，就地增删 | 图片是轻量操作，跳页面反而慢 |
| 是否支持多选 | 不做 | 手机相册多选 + 逐张确认的交互成本高于收益 |
| 复用 `remove` 还是按文件名删 | 复用 `remove(attachmentId)` | 引用计数逻辑已在那里，按名字删会绕过它 |
| 失败处理 | 提示 + 不写半条记录 | 与记一笔一致 |

## 风险

| 风险 | 应对 |
|---|---|
| 两次快速点击导致重复挂图 | 加图时 `_busy` 标志，期间按钮禁用 |
| 删图后备份仍含旧图 | 备份按 `attachmentsOf` 的文件名收集，删记录即不再打包；用例覆盖 |
| 平台通道在测试里不可用 | `pickImage` 可注入，测试用假实现 |
